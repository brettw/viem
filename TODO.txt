Add support for styles inherited across stylesheets (by this I mean the document type variants of plain text/markdown/code in a theme file). I want the "Based on" popup in the Style editor dialog to have a section at the top where it lists the other variants of the stylesheets and the same style name, so if the current one was Line Number in the Code stylesheet, it would say "Plain Text: Line Number"and "Markdown: Line Number", followed by a divider, followed by everything in the current list. Give these items a "Document" icon that matches the appearance of the other icons in the list.

We can only inherit across stylesheets of the exact same named style. We should make sure there are no cycles. Don't allow cycles to be created (if the user selects a style from another sheet that causes a cycle, pop up a modal dialog listing the problem "Code: Line Number" can't depend on "Markdown: Line Number" because that creates a dependency cycle") and reset the "Based on" to be the previous value. This should be rare so I don't want to proactively check for cycles which will slow things down. If we find a cycle when we're resolving a style definition during loading or painting, we should just stop inheritance and use the default builtin values (don't go to the default paragraph font because that may create a cycle also).

When changing the document type popup in the style dialog box, keep the style the same if it exists in the new document type. Only reset it if the current style doesn't exist in the new one.

When the mouse moves over the line number gutter, change to a mouse cursor with the arrow flipped over horizontally (like a left-handed arrow). I want this to match Microsoft Word. If I click, I want it to select that full row of text. If I click and drag vertically, I want it to select that full row I started with and then select by full visible rows. Keep the left handed arrow as I drag and select full rows, always including the full row I started with (so if I drag up, the selection will go from the beginning of the row the cursor is at to the end of the row I started on. And if I drag down, it goes from the beginning of the row I started with to the end of the row the cursor is on.) It would be nicest if you could get the actual system arrow cursor and flip it, but if that's not possible, synthesize one that's black with a white border on Mac, and the reverse color scheme on Windows.

When we're in insert mode, I want the mouse cursor to be the "I-beam" cursor when hovering over the text. When we're selecting by lines from the gutter, keep the left handed cursor. In normal and visual mode, keep the regular arrow. In "selection" mode, use the I beam.

When we're displaying line numbers, one can put the cursor on the "next" line past the end of the document. No line number displays for this line. I want to draw the line number here: any place the caret can go should have a number.

For the line display in the status bar, let's show phsical lines and columns in all cases.

For the status bar, if I set a very thick bottom border, the text mis mis-centered. It looks like maybe it's counting the full status bar size for the centering computation. It should center in the area inside of the padding of the box. And for the status bar at the bottom of the screen, let's position it so the bottom border (if any) is not visible, that position should be just off the edge of the window (so we see the interior padding at the bottom and that's it). The bottom border will be visible for split windows to help separate the viewports, but we don't need that at the bottom.

Likewise, the left and right borders of the status bar should also be just off the view/window when there's a horizontal status bar since this is only a horizontal divider. These borders will be used/visible for vertical splits. The vertical splits will correspondingly have their top and bottom borders just off the view.

On Mac, the style dialog box's preview area and close button move around depending on which tab you have selected (the contents of each tab is different height). The previous area and close button should always be at the bottom and never move. The extra space exposed by a smaller tab should appear between that tab's content and the preview area.

It looks like the vertical scrollbars don't go all the way to the bottom of the view. They should just touch the margin above the status bar. Also make sure it touches the top of the viewport, it looks like there might be a tiny gap but I'm not sure.

Above the lock icon in the block tab of the status dialog, add a label "Match sides". Make it look like the "Background color" label, but make it right-aligned above the lock icon.

We expand/shrink the window when the line number gutter changes size. This creates a problem if a window is opened and edited in certain ways, it will keep expanding. To avoid this, if we save the window size/position we should measure from the top left of the content area not counting the gutter, and the width likewise doesn't count the gutter when saving loading.
